使えないモデルの品質を、足回りで取りに行く

02 — 戦略の核心

埋まらないものと、埋まるものを分ける

埋まらない — capability

一発正答率。重みに刻まれた生の推論力。プロンプトでもスキルでも動かせない。ここを諦める判断が起点。

埋まる — scaffolding

足回り。effort / 並列 subagent / memory / fresh-context 検証。設計でいくらでも積める領域。ここに全リソースを寄せる。

北極星は 設計・要件定義・実装計画への落とし込み力。raw 差より「熟考の深さ／収束前の探索幅／敵対的検証」という scaffolding が効く領域。

03 — 打ち手の全体像

2つの施策で足回りを組み直す

施策 1 — effort-fit advisor

正しい effort

難易度と effort 設定がミスマッチな時だけ /effort 変更を勧告する hook 2本。本番稼働中。

施策 2 — A/B/D スキル改修

設計プロセスの質

brainstorming / writing-plans を改修。探索幅・接地・敵対的検証を設計フローに組み込む。

「正しい effort」と「設計プロセスの質」は直交・補完。両輪で Fable に寄せる。

04 — 施策1 / effort-fit advisor

難易度と effort のズレを、着手前に勧告

05 — 実装 / hook ①

effort を退避する PreToolUse hook

~/.claude/hooks/effort-stash.shbash · PreToolUse
#!/usr/bin/env bash
# PreToolUse hook — 現在の effort を state file に退避
# 根拠: PreToolUse の env にだけ CLAUDE_EFFORT / SESSION_ID が在る（実機確認）
cat >/dev/null 2>&1 || true            # stdin を drain（broken-pipe 回避）
level="${CLAUDE_EFFORT:-}"
sid="${CLAUDE_CODE_SESSION_ID:-default}"
if [ -n "$level" ]; then
  mkdir -p "$HOME/.claude/state"
  printf '%s' "$level" > "$HOME/.claude/state/effort-$sid"
fi
exit 0                                  # ツール呼び出しを絶対にブロックしない
06 — 実装 / hook ②

勧告を文脈注入する UserPromptSubmit hook

~/.claude/hooks/effort-fit.shbash · UserPromptSubmit
#!/usr/bin/env bash
# UserPromptSubmit hook — 現在 effort +「明確ミスマッチ時のみ勧告」を注入
cat >/dev/null 2>&1 || true
sid="${CLAUDE_CODE_SESSION_ID:-default}"
f="$HOME/.claude/state/effort-$sid"
level=""; [ -r "$f" ] && level="$(cat "$f" 2>/dev/null)"
level="${level:-unknown}"             # stash 欠損は unknown にデグレード

# JSON を壊す二重引用符は使わず「」で代用（printf fallback 安全化）
ctx="[effort-fit] 現在effort=${level}。着手前に難易度を評価し、明確にミスマッチ
な時だけ /effort <level> を1行勧告。xhigh寄り=新規アーキ/不可逆選定/複数サブ
システム/深いデバッグ。high以下=局所修正/定型/明確指示。適正なら触れるな。"

if command -v jq >/dev/null 2>&1; then
  jq -nc --arg c "$ctx" '{hookSpecificOutput:{hookEventName:"UserPromptSubmit",additionalContext:$c}}'
else
  printf '{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"%s"}}\n' "$ctx"
fi
exit 0
07 — 実装 / 登録 + 能力境界

settings.json へ登録 ＆ 設計前の実在確認

登録（ユーザーが手動実行）jq
# hook を実行可能に
chmod +x ~/.claude/hooks/effort-stash.sh \
         ~/.claude/hooks/effort-fit.sh

# settings.json へ登録（必ず .bak を取る）
cp ~/.claude/settings.json ~/.claude/settings.json.bak
jq '.hooks.PreToolUse += [{"matcher":"*",
   "hooks":[{"type":"command","command":
   "/ABS/.claude/hooks/effort-stash.sh"}]}]
 | .hooks.UserPromptSubmit += [{"hooks":
   [{"type":"command","command":
   "/ABS/.claude/hooks/effort-fit.sh"}]}]' \
  ~/.claude/settings.json > /tmp/s \
  && mv /tmp/s ~/.claude/settings.json
probe で確定した hook の能力境界
  • ◎ 注入 — additionalContext で文脈注入は可
  • △ effort 読取 — PreToolUse stdin にのみ存在。UPS には無い → stash 方式が必須
  • × effort 変更 — 正規手段なし → 「勧告＋手動トグル」に確定

一度きりの probe（stdin+env ダンプ）で境界を確定 → 手戻りゼロ。

08 — 施策2 / A·B·D スキル改修

設計フローに3つの足回りを差す

A — 多筋フレーミング

brainstorming Phase 2。表層違いの案でなく本質的に異なる軸で発散

B — 敵対的 critic ゲート

承認→計画の間に adversarial-review を fresh-context subagent で挟む

D — Explore 接地

既存コードベース設計は原則 Explore から。読まずに推測で設計しない

共通原則 — 生成は Main・検証だけ subagent。「設計判断はメインスレッドが最も品質が高い」を死守しつつ、検証だけ独立文脈に出す。

09 — A / 多筋フレーミング

2-3案ではなく、2-3の世界観

~/.claude/skills/brainstorming/SKILL.md — Phase 2 抜粋改修後
**発火判定（2段階）— 設計の「探索幅の必要性」で測る
  （実行難易度や effort 設定とは別軸）**
- 非自明な設計        → A（多筋フレーミング）を発火
- 高リスク（不可逆/影響範囲大）→ B（critic ゲート）も発火

1. アプローチを提案
   - 非自明な設計では、表層が違うだけの 2-3 案でなく、本質的に異なる
     フレーミングを 2-3 軸で出す:
       MVP優先 / リスク優先 / ユーザー優先 / 制約優先
     各軸が「何を最大化し・何を捨てるか」を明示する
   - 生成は Main 逐次（"設計生成は Main" 原則。subagent 分散しない）
   - ⚠ 宣言を入れる:「設計モードなので act-don't-survey
     バイアスは適用しない — 収束前に探索幅を意図的に広げる」
10 — B / 敵対的 critic ゲート

自分の設計を、自分以外に殴らせる

~/.claude/skills/brainstorming/SKILL.md — Phase 2 step 6改修後
6. 承認後・敵対的 critic ゲート（高リスク＝不可逆 or 影響範囲大 のみ）
   - 承認と writing-plans 移行の間に adversarial-review を
     fresh-context subagent で挟む（生成 Main・検証だけ subagent）
   - context に設計書パスだけでなく
     「採用理由・棄却した代替案・主要制約」を渡す
       → 検討済みの論点を蒸し返すノイズを防ぐ
   - 検証 subagent のモデルは設計モデルと同等以上
       （能力差があると fresh-context の利得が消える）
   - 棄却された主張は evidence を吟味して設計に反映してから移行
11 — B / 反証パネルの実装

3レンズ × 並列 subagent の Workflow

adversarial-review — Workflow script（3レンズ懐疑役パネル）javascript
const VERDICT = {type:'object', properties:{refuted:{type:'boolean'},
  evidence:{type:'string'}}, required:['refuted','evidence']}
const LENSES = [
  '正確性レンズ: 事実誤認・論理飛躍・古い情報を探して反証せよ',
  '反例レンズ: 主張が崩れる具体的な反例・エッジケースを構築せよ',
  '前提レンズ: 暗黙の前提を列挙し、成り立たない状況を示せ',
]
const results = await Promise.all(args.claims.map(async (claim, i) => {
  // 3レンズを並列起動。「不確実なら refuted=true に倒せ」が肝
  const votes = await parallel(LENSES.map(lens => () =>
    agent(`${lens}\n\n対象の主張: ${claim}\n\nコンテキスト: ${args.context}`
        + `\n\n反証を試みよ。確信を持って反証できる場合のみ refuted=false。`,
      {label:`claim${i}`, phase:'Refute', schema:VERDICT})))
  const refuted = votes.filter(Boolean).filter(v => v.refuted).length
  return {claim, confirmed: refuted <= 1}   // 過半数が落とせねば「確証」
}))
12 — D / Explore 接地

読まずに推測で設計しない（が、追従もしない）

brainstorming/SKILL.md — Phase 1 抜粋
# 既存コードベース設計は原則 Explore から
- 原則 Explore subagent 接地から入る（model: sonnet）
    関連サブシステム・既存パターン・命名規約・制約を把握
- ただし接地は「現状把握」であって
    既存パターンへの追従を強制しない
    # 負債は継続せず改善対象として織り込む
- スキップ可: 新規ゼロ / 1-2 ファイルに自明に閉じる場合
  • 探索はコスト効率の良い Sonnet に投げ、設計判断は Main が握る（棲み分け）
  • 後の自己検証で「接地が下方アンカリングを生む」と指摘され、追従強制でない旨を明記

15 — 棄却から得た修正

反証は、そのまま設計改善になった

Claim4 — 自己矛盾

「非自明＝常時発火」が adversarial-review 自身の「高リスク判断専用」原則と矛盾 → B を高リスク（不可逆/影響範囲大）のみに絞った

Claim7 — 軸違い

effort-fit は実行難易度、発火判定は設計探索幅。目的関数が別 → 連動を切り A/B を2段階閾値に分離

Claim3 — 能力差

検証 subagent が Sonnet だと fresh-context の利得が消える → 検証モデルは設計モデルと同等以上＋棄却済み代替案を context に渡す

Claim6 — アンカリング

Explore 接地が既存パターンへの追従を誘発 → 「接地＝現状把握／負債は改善対象」と明記し「禁止」を緩和

16 — 横展開できる原則

この案件から持ち帰れるもの

  • capability と scaffolding を分離する — 諦める領域を決めると打ち手が定まる
  • 責務分離 — 意味判断はモデル、機械的な状態供給は hook
  • 生成は Main・検証は fresh-context — エラー相関を切る棲み分け
  • プリミティブ実在確認を設計の前に — probe 一発で能力境界を確定し手戻りゼロ
  • 自己批判より独立検証（ただし能力差・文脈飢餓に注意）
  • ドッグフード — 作った検証機構を自分に向ける。過剰な正当化が即座に剥がれる
