# Tools 紹介ページの文言監査 — 設計書

作成: 2026-10-16 / 状態: CEO 承認待ち

## 1. 目的と背景

NOCTA の HP（`website/`）に Tools を追加・改修するとき、紹介ページの文言の問題を、CEO が push を頼む前の段階で毎回自動で見つける。見つけたら「ここが気になる」を並べ、直した版を用意する。出すかどうかは CEO が決める。

きっかけは 2026-10-16 の Barside 紹介ページ。CEO の言葉:

- 「説明ページになっていることが気に障った。ここはアプリの簡単な紹介で、細かく説明するページではない」
- 「裏の仕組みや、私だけが知ればいいことが多分に含まれていた」

CEO の直しはほぼすべて「消して」だった（「聞き返していい」「旅先のバー」「夜を数える」の項目、仕組みの「相手の言葉」「相手の声」「画面」、締めの「カウンターの最後の灯り。」の飾り）。直し方も、言い換えより削除が基本になる。

## 2. ゴール / 非ゴール / アンチゴール

ゴール:
- 紹介ページか Tools カードの説明文を含むコミットのたびに、監査が自動で走る（Claude が覚えていなくても走る）
- 監査は 2 段にする。機械的に数えるチェックと、手本（lampnook）と比べて読むチェック
- 結果は「消す / 短くする / 残す」の一覧と、直した版。直した版は削除側に寄せる
- 既存の公開済みページにも一度かけ、修正前後を CEO に見せる。CEO の採否をルールに戻して基準を強くする

非ゴール:
- 監査で push を止めること。push の判断は今までどおり CEO が行う
- GitHub Actions 側での検査。CI は直せないため、今回は入れない
- 外部リポジトリのページ（NuWord・Inner Canvas・barside-app.github.io）本体の監査。ただし、それらの `apps-data.js` のカード説明文は対象にする

アンチゴール（動いても失敗とみなすもの）:
- 直した版で SVG・見本・画像の行が消える
- 文言を言い換えて、長さが同じまま「AI っぽい別の文」になる
- 監査結果が長く、CEO が読むのに手間がかかる（一覧は 1 ページあたり 10 行程度に収める）
- 新しい指摘を足すたびに、hook やスクリプトのコードを書き換える必要がある

## 3. 判断の基準（ルールの正本に載せる中身）

中心の問い: **「初めて来た人が、試す前にこれを知りたいか」**。答えが「いいえ」なら削る。

- 紹介ページはアプリの簡単な紹介であって、説明書ではない
- 構成は lampnook を手本にする。見出し、ひとことの説明、入口のボタン、短い項目の順
- 各項目は 1〜2 文。項目の数は、迷ったら少ないほうにする
- 書かないもの:
  - 作者用の情報（灯りの表示・接続トークン・作者用の使い方・作者の Mac）
  - 技術名・サービス名（Tailscale・sql.js・FSRS・ElevenLabs・three.js・IndexedDB・PWA など）
  - 使えば分かる細かい挙動（「聞き返すと少しゆっくり返ってくる」「通算 N 夜で数える」）
  - 作り手の事情（「AI に書かせない理由」など）
  - 更新履歴のような見出し（「この秋、増えたもの」）
- 仕組みは原則書かない。残すのは、訪問者が使うかどうかを決めるのに要ることだけ（例: 記録はブラウザの中だけに残る）
- 締めの一文は飾りを付けず、言いたいことだけ（例:「うまく話せなくても、大丈夫。」）
- 手描きの SVG・見本・画像は残す。直すのは文言だけ

## 4. 構成

### 4.1 ルールの正本: `docs/tools-page-copy.md`

- 第 3 節の基準を、文章と機械可読のリストで持つ。リストは禁止語、禁止見出しの型、文の数の上限、カード説明文の文字数の上限、**監査対象の紹介ページの一覧**
- 紹介ページの一覧（初期値: `website/lampnook/index.html` / `website/barside/index.html`）。紹介ページとは「アプリの簡単な紹介を挟み、そこから入口のボタンでアプリ本体へ進む」形のページを指す。アプリ本体の画面（strategy・kihi・iro・flora・gems・still の `index.html` など）は対象にしない（CEO 決定 2026-10-16）
- 今後の Tools でこの形を取るものは、紹介ページを作った時点で一覧に足す。これで自動的に監査の対象になる（CEO 決定）
- 機械可読のリストは、ファイル内のコードブロックに置く。スクリプトはそれを読む
- 新しい指摘はこのファイルに足すだけで効く（アンチゴール 4 への対応）
- 置き場所は `website/` の外にする。`website/` は丸ごと公開されるため
- `website/CLAUDE.md` に 1 行のポインタを置く
- English プロジェクトのメモリ `nocta-intro-page-copy.md` は、この正本へのポインタに置き換える。そのメモリにある「最後に残ったもの」の記録は、正本の事例欄に移す

### 4.2 機械チェック: `scripts/copy-lint.py`（Python 3、標準ライブラリのみ）

入力: 監査するファイル（`website/<tool>/index.html` / `website/apps-data.js`）と、比較元（既定は `HEAD`）。

見ること:
1. `<svg`・`<img`・見本ブロックの数が、比較元より減っていないか（減っていれば最重要として報告）
2. 正本の禁止語・禁止見出しが本文に含まれていないか（タグと SVG を除いた、見える文字だけを対象にする）
3. 各項目の段落（`<p>` / `<dd>`）の文の数（「。」で区切る）が上限を超えていないか
4. `apps-data.js` の `descJa` が文字数の上限を超えていないか

出力: 1 行 1 件のテキスト（`種別 / 場所 / 抜粋`）。終了コードは、SVG が減ったら 2、それ以外の指摘があれば 1、なければ 0。

### 4.3 読んで判断するレビュー役: エージェント `copy-auditor`

- 定義は `~/.claude/agents/copy-auditor.md`（版管理コピーは `claude-config/agents/`）。モデルは Opus 5（R-09 の批評枠）。ツールは Read / Grep のみで、編集はしない
- 毎回、正本・lampnook の `index.html`・対象ページ・copy-lint の結果を読む
- 返すもの: 項目ごとの「消す / 短くする / 残す」と、その一言の理由。「短くする」には置き換え後の文言を付ける
- 迷ったら「消す」に倒す。言い換えで長さを保つ案は出さない

### 4.4 自動で走らせる仕掛け: PreToolUse hook `copy-audit-guard.sh`

- 置き場所は `~/.claude/hooks/`（版管理コピーは `claude-config/hooks/`）。登録はユーザー設定 `~/.claude/settings.json` の `PreToolUse`（matcher: Bash）
  - プロジェクト設定にしない理由: NOCTA の HP は `~/NOCTA` で開いたセッションからも、English などほかのプロジェクトのセッションからも触られる。今回の Barside もそうだった。どこから触っても走るようにする
- 動き:
  1. Bash のコマンドに `git commit` が含まれ、かつ対象が NOCTA リポジトリであるときだけ反応する。リポジトリは `cd <dir> &&` / `git -C <dir>` / 作業ディレクトリから割り出す
  2. 次のどちらもなければ、何もせず通す（アプリのコード修正で止めないため。私の判断）
     - ステージされたファイルに、正本の一覧にある紹介ページが含まれる
     - `website/apps-data.js` の `descJa` / `descEn` の行が変わっている（`url` や `icon` だけの変更は通す）
     - `apps-data.js` に新しい項目が増え、その `url` が一覧にないローカルページを指すとき: 止めずに「紹介ページの形なら一覧に足すか」を CEO に確かめるよう Claude に伝える
  2b. 1 つのコマンドの中で `git add <対象>` と `git commit` がつながっている場合: hook が動く時点ではまだステージされていないので、対象ファイルが引数に含まれていれば拒否する。「add と commit を別々の Bash で実行せよ」と返す。`git commit -a` / `-am` も同じ扱い（私の判断）
  3. ステージ内容の木のハッシュ（`git write-tree`）に対応する監査済みの印（`.git/copy-audit/<hash>`）があれば通す
  4. 印がなければ copy-lint を実行し、コミットを拒否（deny）する。拒否の理由として、lint の結果と「copy-auditor で監査し、結果と直した版を CEO に見せ、CEO の OK のあとで印を付けて再コミットせよ」という指示を Claude に返す
- 印は、CEO が監査結果を見て OK を出したあとに Claude が付ける。ページを直せばハッシュが変わるので、もう一度監査が要る
- `.git/` の中に置くので、印は git に入らない
- 印を CEO の OK なしに付けて hook を回避することは禁止する。R-02 の approved-guard と同じ扱いで、正本の CLAUDE.md に一文足す
- 失敗時（スクリプトの例外など）は通す（fail-open）。ただし「監査を実行できなかった」と Claude に伝える

### 4.5 CEO に見せる形（毎回）

- 「ここが気になる」の一覧（10 行程度）。最初に SVG が減っていないかの結果を書く
- 直した版を作業ツリーに反映した状態で、項目ごとの修正前と修正後の文言
- 「出すかどうかは CEO が決めてください」と添える。項目ごとに戻したいものを言えるようにする

## 5. 既存ページへの一回目の監査

対象:
- 紹介ページ 2 つ: lampnook / barside
- `apps-data.js` のカード説明文 11 件（strategy・kihi・iro・flora・gems・still・NuWord・Inner Canvas を含む全件）
- アプリ本体の画面の文言は見ない（CEO 決定 2026-10-16）

進め方:
1. 新しいブランチ `copy-audit/2026-10` で作業する（main を汚さない）
2. 各ページに copy-lint と copy-auditor をかける
3. 直した版を作り、文言だけを Edit で置き換える
4. 修正前後を 1 つのページにまとめて CEO に見せる。ページごとに次を並べる:
   - 監査の一覧
   - 項目ごとの文言の前後
   - 320px と 1280px の前後のスクリーンショット
5. CEO はページごと・項目ごとに採否を決める
6. 採否のうち基準に効くもの（「これは残してよい」「これも消す」）は、正本の基準と事例欄に足す。仕組みの強化はここで行う
7. 採用分だけをコミットする。push は CEO の指示を待つ

lampnook は手本なので、監査で指摘が出た場合は基準の側を疑う材料として扱う。

## 6. 受け入れ条件

- Barside の 633b183 直前の版（`633b183^:website/barside/index.html`）に copy-lint をかけたとき、技術名（Tailscale など）と作者用の情報が指摘される
- 同じ版に copy-auditor をかけたとき、CEO が実際に消した項目の大半が「消す」と判定される
- SVG を 1 つ消したテスト用の差分で、copy-lint が終了コード 2 を返す
- 紹介ページを変えたコミットを試みると hook が拒否する。印を付けたあとの同じステージ内容なら通る。対象外のファイルだけのコミットは素通りする
- iro の `index.html` だけを変えたコミット、`apps-data.js` の `url` だけを変えたコミットは素通りする
- `git add website/barside/index.html && git commit ...` を 1 つのコマンドで実行すると拒否され、分けるよう返ってくる
- 既存ページの一回目の監査の結果ページを CEO が開き、ページごとに採否を決められる

## 7. 作る人に任せること

- copy-lint の HTML の取り出し方（標準ライブラリの `html.parser` でよい）と、禁止語リストの初期値の細部
- 文の数の上限（目安は 2）とカード説明文の文字数の上限（目安は 60 字。現状のカードを見て決めてよい）
- 一回目の監査の結果ページの見た目
- hook のコマンド文字列の解析の細部。取りこぼしは「通す」側に倒してよい。拾い過ぎて関係ないコミットを止めるほうを避ける
