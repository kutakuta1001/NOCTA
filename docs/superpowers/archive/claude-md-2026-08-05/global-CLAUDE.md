## G-01: モデルを目的で使い分ける

- **Haiku 4.5**: 調査・短いファイル生成・ドキュメント更新（最安・$1/$5/MTok・コンテキスト200k・拡張思考対応あり）
- **Sonnet 5（起案者 / Drafter）**: 仕様書・草稿・コード生成（デフォルト）`claude-sonnet-5`・$3/$15/MTok（導入価格 $2/$10・2026-08-31まで）・コンテキスト1M・最大出力128k・ナレッジカットオフ2026年1月・適応的思考あり（旧 Sonnet 4.6 から移行・2026-07-04）
- **Opus 5（批評者 / Critic）**: 重要設計レビュー・複雑なコード生成・クリティーク。`claude-opus-5`・$5/$25/MTok（Opus 4.8 と同価格）
  ※ 2026-07-24 GA・公式掲載済み。適応的思考あり・拡張思考なし・コンテキスト1M tokens（≒555k words）・最大出力128k tokens・ナレッジカットオフ2026年5月・SWE-bench Pro 79.2%（報道値・Opus 4.8 は 69.2%）
  Batch API betaヘッダー（output-300k-2026-03-24）使用時はOpus 5/Sonnet 5ともに最大300k tokens出力可能
  重要レビュー・コーディング系タスクには `/effort xhigh` 推奨
  /fast コマンドで同じ知能を高速で利用可能（Fastモード: $10/$50/MTok・対象は Opus 5・4.8）
  hooks から `CLAUDE_EFFORT` 環境変数を参照可能（v2.1.133〜）
  Opus 4.8（`claude-opus-4-8`）はレガシー: Opus 5 障害時のフォールバックとして当面利用可
- **Fable 5（最上位・深い推論枠）**: `claude-fable-5`・$10/$50/MTok・Anthropic 最高性能の一般提供モデル（Mythos級・Opus の上位）。輸出管理による断続提供リスクは残るが **2026-07-29 時点で GA 継続・終了日未定**（旧想定「2026-07-07 以降利用不可」は実現せず）。**深い推論が必要なタスク（超重要クリティーク・複雑な設計判断）では第一候補**として `/model claude-fable-5` で手動選択。恒常 fallback は Opus 5
- **Sonnet 5（拡張思考は非対応）**: 深い推論は適応的思考 + `/effort` で制御（Sonnet 5 は拡張思考なし）
- **起案→批評フロー**: Sonnet 5 が草稿 → Opus 5 が批評・代替案提示 → 最終選択（重要設計変更時に適用。深い推論が必要な案件・判断が割れる超重要案件は Fable 5 にエスカレーション）
- **Agent Teams**: 全員 Sonnet 5 開始、レビュー時 Opus 5 切替
- **Opus 5 切替通知ルール（デフォルトは Sonnet 5）**: 以下のタイミングになったら作業前に「Opus 5 への切り替えを推奨します: `/model claude-opus-5`」と通知し、CEO の確認を待つ。切り替え不要と言われたら Sonnet 5 のまま続ける。
  - **superpowers スキル使用時（全種）**: brainstorming / systematic-debugging / writing-plans 等、superpowers: プレフィックスを持つスキルを呼び出す前
  - 重要設計レビュー・CLAUDE.md 等の重要設計変更のクリティーク
  - Agent Teams のレビューフェーズ
  - 出力が 64k tokens 超になる見込みの大型タスク

コスト最適化: 単純タスクは `/effort low` / 標準は `/effort high`（デフォルト）/ 最重要は `/effort xhigh`

モデル棲み分け詳細・変更履歴・新プロジェクト向けテンプレートは `~/.claude/references/model-lineup.md` を参照。
新モデルリリース時は `/model-review` スキルで棲み分けを再議論する。

## G-02: ファイル読み込みは最小限

セッション開始時は context.md と handoff.md のみ読む。他は必要な瞬間に読む。
既存コードへの変更・機能追加時は、変更対象ファイルを実装前に Read して関連ファイルを把握する。

---

## G-03: ドキュメントに絵文字を使わない

仕様書・handoff.md・コードコメントには使わない。SNS投稿文・プレゼン資料のカジュアル版のみOK。

---

## G-04: 対話してから作業する

Goサインなしにファイル生成を開始しない。
プロンプト品質の3Cルール: Concise（簡潔）・Contextual（文脈に沿う）・Constrained（制約付き）。
初回プロンプトには **Goal（目的）+ Constraints（制約）+ Acceptance criteria（完了条件）** を一括して渡す。逐次指示より初回一括の方が精度が高い。

---

## G-05: セッションが切れても再開できる状態を保つ

作業完了時に handoff.md を更新。進行中タスクは drafts/ に保存。handoff.md は「完了した事実」と「次のアクション」のみ1〜3行で記述する。

---

## G-06: 納品デブリーフ — 未知を減らす（Blind Spot Pass）

高性能モデルほど人間の曖昧さが成果物に出る。作業中に都度質問して手を止めるのはもったいないので、
気づきをサイレントに溜め、**納品物と一緒にまとめて示す**。目的はCEOの次の依頼を鋭くすること。

**作業中（サイレント記録・ブレスト/設計/実装は止めない）:**
- 盲点: CEOが気づいていなさそうな前提・リスク・機会
- 判断メモ: 仕様の解釈・保守的に倒した判断・依頼と成果物のズレ（implementation-notes）
- 比較: 類似アプリ・デザイン・サービスとの比較で見えた差分と、あえて採用しなかった良い要素
- 質問の種: 依頼で曖昧だった点・先に指定があれば精度が上がった点

**納品時（最終報告の末尾に「デブリーフ」節として提示）:**
1. 盲点（3件以内・重要度順）
2. 実装中の判断とその理由（3件以内。迷って保守的に倒した箇所を優先）
3. 類似サービス比較からの示唆（採用/不採用と理由。次回検討の候補）
4. 次の依頼を鋭くする質問（2〜3問。回答は任意・返答がなくても作業は完結している状態にする）
5. **次回の依頼文テンプレ**: 「次回はこう頼むと一発で伝わる」1〜2文の具体例

**運用:**
- 適用範囲: 非自明な制作・実装・設計タスクのみ。単発質問・微修正・定型作業には付けない（ノイズ防止）
- 例外: 破壊的操作・スコープの根本変更に関わる判断だけは従来通り作業中に確認する
- 希望時のみ: 成果物の理解を確認する3問クイズ（Explainer/Quiz）を追加できる
- デブリーフの質問にCEOが答えた内容は、次回作業の前提として handoff またはプロジェクト CLAUDE.md に反映する

## COST POLICY

| 状況 | モード |
|---|---|
| 全体計画・タスク分解 | Plan Mode |
| 単発タスク | Subagent |
| 複数領域の並列作業 | Agent Teams |

Agent Teams は大型フェーズ（プロジェクトで2〜3回程度）のみ推奨。コスト肥大に注意。

**Agent Teams 3役モデル:**
- **explorer（調査）**: 情報収集・調査 → Haiku 推奨
- **architect（設計）**: 仕様書・構成決定 → Sonnet 推奨
- **executor（実行）**: ファイル生成・実装 → Sonnet / 品質重要な場面は Opus

## スキル・CLAUDE.md 設計

- CLAUDE.md には**常時適用ルールのみ**記載。状況限定ワークフローはスキル（`~/.claude/commands/`）に分離する。
- スキルファイルは **500行以内**を目安。詳細情報は `references/` ファイルに分離し段階的開示でコンテキストを保全。
- v2.1.117〜: スキル frontmatter の `context:fork` / `agent` / `mcpServers` フィールドをエージェントスキル設計に活用可。v2.1.218〜 `context:fork` スキルはデフォルトでバックグラウンド実行（同期実行には `background: false` を明示）。サブエージェントは同時実行上限20・ネスト深さ3（v2.1.219）。
- v2.1.142〜: プロジェクトルートの `SKILL.md` がプラグインスキルとして自動検出される。

## フロントエンド作成（frontend-design）

新しいHTMLページ・UIコンポーネントを作成、または既存UIを大幅改修するときは、コード生成前に `frontend-design:frontend-design` スキルを呼び出す（全プロジェクト共通・汎用AIデザインの回避とデザイン品質確保のため）。
プロジェクト固有のブランド指定（配色・フォント・トーン）がある場合はそれを優先し、スキルに渡す。自明な小変更（1要素の修正・定型）には適用しない。

UI 作成・改修時は `~/designer/INDEX.md`（デザインパターン索引・1 行/件）も読み、該当パターンがあればレシピ（`~/designer/patterns/`）を参照して適用する。適用したらレシピの used_in に `{project, date}` を記録する。任意のタイミングでの検索は `/design-search`、新規記事の蓄積は `/design-extract`。frontend-design と同様に自明な小変更には適用せず、レシピがプロジェクト固有のブランド指定と競合する場合はブランド指定を優先する。

## コードレビュー（Codex CLI）

`/review [計画書]` / `/review-diff` — Codex CLI を第三者レビュアーとして呼ぶ（全プロジェクト共通）。

ユーザー確認の上で API 従量課金（apikey モード）にフォールバックする。
