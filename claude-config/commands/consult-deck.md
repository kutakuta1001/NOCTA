# /consult-deck — 資料作成（仮想コンサルチーム）

コンサルタント3名（EM・アナリスト・パートナー）で資料を作る。工程は直列依存のため並列化しない。
書式・規約は `~/.claude/commands/references/consulting-common.md` に従う。

## Step 0: 引数検証と段取り

1. 引数が空なら「テーマを指定してください。例: `/consult-deck 新規事業Xの参入判断資料`」と表示して終了
2. **目的・読者・キーメッセージ**の3点を確認する。引数や会話の文脈から自明な項目は質問しない（G-04）。
   全部不明なときだけ、3点を1回のメッセージでまとめて聞く
3. 出力先を決める:
   - 進行中のエンゲージメント文脈があれば、その `~/consulting/[slug]/` を使う
   - なければ consulting-common.md「エンゲージメント規約」の slug 規則で新規作成し、engagement.md を初期化する

## Step 1: ゴーストデック（骨子レビュー・ゲート）

`consultant-em` を Agent tool で起動する。渡すもの:
- テーマ・目的・読者・キーメッセージ、engagement.md のパス
- 指示: 「ゴーストデック（各スライドのアクションタイトル+狙い1行のみ）を作成。
  consulting-common.md の『Markdown デック書式』の規則でタイトルは主張文にする。スライド数の目安は10±5」

**ゲート:** ゴーストデックを CEO に提示し、承認・修正指示を待つ。
CEO が事前に一括委任している場合はその旨を明記してデフォルト続行し、納品時に骨子の判断理由を報告する。

## Step 2: エビデンス収集

承認された骨子から必要エビデンスを洗い出し、`consultant-analyst` を起動する。渡すもの:
- 承認済みゴーストデック、engagement.md のパス、inputs/ にある CEO 提供資料の一覧
- 指示: 「スライドごとに必要なデータ・事実を収集。3ラベル原則・出典必須・検算必須。結果は analysis/ に保存」

エビデンス量が多い場合（10スライド超で全て要データ）はスライド群を2〜3分割し、analyst を最大3体まで1メッセージ内で並列起動してよい。

## Step 3: 本文ドラフト

`consultant-em` を起動する。渡すもの:
- 承認済みゴーストデック、analysis/ の分析メモ一覧
- 指示: 「『Markdown デック書式』で本文を作成。分析メモに無い数値・事実は創作せず『追加分析が必要』と注記。
  ドラフトは deliverables/ ではなく analysis/draft-deck.md に保存」

## Step 4: パートナーレビュー

`consultant-partner` を起動し、ドラフトをレビューさせる（出力契約・判定三択）。
- 🔴🟡 の指摘は `consultant-em` に修正指示を出して反映（修正は EM。パートナーは修正しない）
- 差し戻しの場合は修正後にパートナー再判定（最大2ラウンド。収束しない場合は CEO に論点を提示）

## Step 5: 納品

1. 完成版を `deliverables/[日付]-[テーマslug]-deck.md` に保存
2. engagement.md の進捗・次アクションを更新（各1〜3行）
3. CEO に納品報告: 結論サマリー・骨子からの主な変更点・未確認事項
4. HTML 化の希望を確認する。手段は3段階（consulting-common.md「デザイナー部隊との協業」参照）:
   - **テーマ選択（既定）**: `~/consulting/themes/THEMES.md` の一覧を提示（見本比較はギャラリー
     `~/consulting/themes/index.html`）。CEO 指定のテーマ（無指定なら編集レポート）の見本を踏襲して
     frontend-design スキルで変換。手順は THEMES.md の「HTML 化の手順」に従う
   - **競作（勝負資料・対外 LP）**: /design-team を起動。ブリーフは協業規約の必須項目に従い、
     中身不変条項と出力先 `[engagement]/drafts/design-team/` を必ず含める
   - **一般人評価（B2C 向けのみ）**: 完成後に /design-review-public を案内する（自動実行しない）
5. デザイン完成後、deck md と HTML の数値・出典を突合する。欠落・改変があれば
   /consult-check の K1/K3 を起動して精査する（中身がデザインで壊れていないことの確認）

## IMPORTANT（制約）

- 1スライド1メッセージ・アクションタイトル・So What 行・出典行を欠くスライドを納品しない
- 分析結果に未検証変数がある場合、「未検証変数一覧」スライド（変数名・仮置き値・感度・検証方法）を必ず1枚含める（結論の前提を隠さない）
- 出典なしの数値・事実をスライドに載せない（推定・仮説はラベル明記）
- Step 1 の骨子承認前に Step 3 のドラフトへ進まない（方向違いの大量作業の防止）
- 細部まで固い品質が必要な資料（対外提出・経営会議）には、納品前に `/consult-check` の実行を提案する。
  対外提出資料はさらに `/codex-review [パス]`（Codex 第三者レビュー）も案内する（自動実行しない）

## 棲み分け

- 楽曲LP・プロダクトLP → /lp-create
- HTML UI の作り込み → frontend-design スキル
- 資料の中身の分析が未了 → 先に /consult-analyze
