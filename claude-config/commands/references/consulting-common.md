# consulting-common — 仮想コンサルチーム共通規約

コンサルハーネス（/consult, /consult-deck, /consult-analyze, /consult-decide, /consult-check, /consult-sparring）と
3エージェント（consultant-analyst / consultant-em / consultant-partner）が共有する規約・書式集。
各スキルは必要な節だけを参照する（全文を読む必要はない）。

---

## エンゲージメント規約

コンサル業務の成果物はすべて `~/consulting/[engagement-slug]/` に置く（NOCTA等のプロジェクトを汚染しない）。

**共有資産 `~/consulting/_firm/`**（エンゲージメントではない・全案件が参照する）:
- `knowledge.md` — ファームナレッジ台帳（検証済みの事実と学び。「ファームナレッジ」節参照）
- `playbooks/` — 再利用可能な「解き方」（「プレイブック書式」節参照）

**slug 生成規則:** 議題を小文字化し、スペース・記号をハイフンに変換、連続ハイフンは1つに（/research と同じ正規化）。

**ディレクトリ構造:**

```
~/consulting/[engagement-slug]/
├── engagement.md      # 状態管理（下記テンプレート）。セッション再開点
├── inputs/            # CEO 提供資料
├── analysis/          # 分析メモ・データ・検算ログ（アナリストの作業場）
└── deliverables/      # 納品物（デック・レポート・メモ）
```

**engagement.md テンプレート（各節1〜3行で簡潔に。SteerCo 議事録のように更新する）:**

```
# エンゲージメント: [議題]
開始日: YYYY-MM-DD / 状態: 進行中 or 完了

## 論点
（何に答えるためのエンゲージメントか。主論点1つ+副論点）

## 仮説
（現時点の最有力仮説。更新したら日付を添えて上書き）

## 型と変数
主型: [型名]（選定理由1行）
- 検証済み: [要素名]=[値]（事実/推定）
- 検証中: [要素名] — [検証方法]
- 未検証: [要素名]（感度 高/中/低）

## 進捗
- YYYY-MM-DD: （完了した事実のみ）

## 決定事項
- YYYY-MM-DD: （CEO の決定・承認）

## 次アクション
（1〜3行）
```

## エージェントの起動と受け取り

成果物が返ってこない事故を防ぐための規約（2026-08-26 追加。transcript の実測に基づく）。

- **`name` を付けて起動しない。** `name` 付き（mailbox 方式）で起動したエージェントは最終
  メッセージが依頼元に返らない。届くのは `idle_notification` だけで本文はゼロバイト。
  `name` なしで起動すれば task-notification に全文が付いて返る
- 実測: partner を `name` 付きで起動した3回（2026-08-25〜26）はレビュー本文 42,091 字が
  すべて届かず transcript に残っていた。再送を依頼した分も同じ経路で消えた。
  同時期に `name` なしで起動した2回は届いている
- チームで相互に SendMessage させるため `name` が必要な場合は、依頼文に
  「**結果は SendMessage で全文送ること。ターンを終えるだけでは届かない**」を必ず入れる
- 指摘のみを出す役（partner）に「ファイルには書かない」と指示すると配送経路が
  SendMessage だけになる。禁じるときは同じ依頼文で送信方法を指定する

## 出力契約と重大度

レビュー・チェック系の指摘はすべて次の形式に従う（/persona-review と同一規約）:

```
[重大度] 指摘内容 — 根拠: 位置（ファイル・スライド番号・行）or 再現手順
```

**重大度定義:**

| 表記 | 意味 |
|------|------|
| 🔴 | 結論を覆す誤り・信頼を毀損する誤引用/誤計算・重大リスクの見落とし |
| 🟡 | 個別箇所の誤り・弱い根拠・エッジケースの見落とし |
| 🟢 | 改善余地・表現の向上提案 |

**厳守事項:**
- 根拠を示せない懸念は指摘にせず「未確認事項」として分離する（推測で埋めない）
- 指摘専任の役割（チェッカー・レビュアー）は修正を行わない。修正は本体セッションが CEO と判断する
- 指摘0件なら「指摘なし」と明記する（沈黙しない）

## 3ラベル原則

すべての成果物で、主張を次の3ラベルに分類して表記する。推測と事実が同じトーンで並ぶことを禁止する。

| ラベル | 条件 | 表記例 |
|--------|------|--------|
| 事実 | 出典URL または CEO 提供資料で確認済み | 「国内市場は約1.2兆円（事実・出典: URL）」 |
| 推定 | 計算・推論の根拠を示せる | 「シェア5%なら売上600億円（推定・根拠: 上記市場規模×5%）」 |
| 仮説 | 未検証。検証方法を添える | 「若年層ほど解約率が高い（仮説・検証: コホート分析）」 |

## 型カタログ

一般論で考えを膨らませない。**問いのタイプに合う「型」をまず見極め、その要素を埋めることで考える。**
問いのタイプから主型を引く対応表:

| 問いのタイプ | 主型 | 要素（＝変数になるもの） |
|---|---|---|
| 事業モデル全体の筋 | ビジネスモデルキャンバス | 顧客セグメント/価値提案/チャネル/顧客関係/収益の流れ/主要リソース/主要活動/キーパートナー/コスト構造 |
| 新規事業・アイデア検証 | リーンキャンバス | 課題/解決策/独自の価値提案/圧倒的優位性/顧客セグメント/主要指標/チャネル/コスト構造/収益の流れ |
| 実現可能性 | フィージビリティチェック | 納期/技術/コスト/人・体制/法規制 |
| 他社への優位性 | VRIO（補助: バリューチェーン） | 経済価値/希少性/模倣困難性/組織 |
| 市場・競合の構造 | 3C（補助: 5Forces） | 顧客/競合/自社（+5つの力） |
| 協力者・競合・利害 | ステークホルダーマップ | 協力者・競合・中立の分類×影響度×関心度 |
| 成長の方向 | アンゾフマトリクス | 既存/新規×製品/市場の4象限 |
| 外部環境の変化 | PESTEL | 政治/経済/社会/技術/環境/法 |
| 課題の特定 | As-Is/To-Be+イシューツリー | 現状/あるべき姿/ギャップ/原因 |
| 出願・知財戦略の判断 | 知財事業化チェック | 発明の強さ（新規性・回避容易性）/事業適合（自社実施・ライセンス・防衛）/公開 vs 秘匿/コスト・維持（出願・審査・年金）/権利行使の実効性（侵害検知性） |

**規則:**
- 主型は1つ、補助型は最大1つ。型の重ね掛けで網羅した気にならない
- カタログに合う型がなければ無理に当てず、要素分解を自作して「自作型」と明示する

## 型先行プロトコル

型を使って「要素を変数として検証を重ねる」5ステップ。実施主体を各ステップに明記する。

1. **型選定**（EM）— 問いのタイプを判定し、型カタログから主型（+補助型最大1つ）を選ぶ。
   選定理由を1行で明示する
2. **要素充填**（EM）— 型の全要素を3ラベル（事実/推定/仮説）で埋める。埋まらない要素は
   「空欄」のまま残す。**空欄と仮説が「検証すべき変数」**（埋まらないことが発見）
3. **感度ランキング**（EM）— 各変数に「この要素の値が変われば結論が変わるか」で
   感度 高/中/低 を付ける
4. **ハイブリッド検証**（本体セッションが analyst 起動）— 感度「高」の上位1〜2個のみ自動検証
   （analyst による実査 or 手元データ・Bash検算）。残りは**未検証変数一覧**
   （変数名・現在の仮置き値・感度・検証方法）として成果物に必須掲載する
5. **更新と再判定**（EM+本体セッション）— 検証結果で型を更新し、結論が変わるかを再判定。
   engagement.md の「型と変数」節に状態を記録する（次セッションは検証の続きから再開できる）

## Markdown デック書式

**経営向け三点セット（詳細版・要点版・説明版）を作る場合は `~/consulting/_firm/playbooks/executive-factbook.md` に従う。**
中核: 説明版は「迷ったら削る」（消す内容は詳細版へ保存してから）／表2つで言えることは2軸グラフ1枚に／
用語は聞き手の言葉へ／本編＋別紙の二部構成でストーリー本筋を守る。

デック（資料）は1ファイルの Markdown で、スライドを `---` で区切る。

**規則:**
- 1スライド1メッセージ。見出しはアクションタイトル（名詞の羅列でなく主張文。例: 「市場成長は都市部に集中しており、初期展開は3都市に絞るべき」）
- 本文は3〜5行の箇条書き or 表1つ。詰め込まない
- 各スライド末尾に `So What:`（このスライドが結論に効く理由・1行）と `出典:`（3ラベル原則に従う）
- 冒頭にエグゼクティブサマリー1スライド（結論+根拠3点+推奨アクション）

**スライド例:**

```
---
## 競合の値下げは体力勝負であり、追随せず差別化で応じるべき

- 競合A社は主力製品を15%値下げ（事実・出典: URL）
- 同社の営業利益率は3%であり値下げの持続性は低い（推定・根拠: 決算資料）
- 当社の解約理由の1位は価格でなく機能不足（事実・出典: inputs/解約調査.md）

So What: 価格追随は消耗戦。機能差別化が防御と攻撃を兼ねる
出典: 上記各行に記載
---
```

## デザイナー部隊との協業

資料・LP の見た目を高めたいとき、デザイナー部隊（/design-team の凛・華・紡、/design-review-public の一般人評価者、~/designer のパターン庫）と協業する。

**責任分担:**

| 領域 | 責任者 |
|---|---|
| 中身（ロジック・ファクト・ストーリーライン・出典） | コンサルチーム（EM 確定・パートナー承認済みの状態で渡す） |
| 見た目・体験（レイアウト・タイポグラフィ・演出） | デザイナー部隊 |
| 採否の判断 | CEO（design-team の既存判断ゲート） |

**イメージ図（体験図・ビジョン図）の生成ツール【CEO決定 2026-08-29】:** Claude Design は使わず
**ChatGPT・NotebookLM・Gemini 系に依頼する**。依頼は自己完結の入力 Markdown で行い、資料側には
PNG 上書きだけで差し替わる口を用意する（手順の詳細は executive-factbook.md）。

**使い分けの3段階:**

| 場面 | 手段 | コスト |
|---|---|---|
| 日常の資料 HTML 化 | テーマ選択（既定・themes/THEMES.md） | 小 |
| 勝負資料・対外 LP | 競作（/design-team・3案から CEO が選ぶ） | 大 |
| B2C・一般読者向けの最終確認 | 一般人評価（/design-review-public・案内のみ、自動実行しない） | 中 |

**協業規約:**

1. **中身不変の原則** — デザイナーへのブリーフに必ず含める:
   「テキスト・数値・出典・スライド構成は変更禁止。変更したい場合は指摘として返す（勝手に直さない）」
2. **ブリーフ必須項目** — コンセプト1行 / 読者と目的 / 実コピーの源（承認済み deck md のパス）/
   テーマ制約（既存テーマ踏襲 or 自由提案）/ 中身不変条項 / 出力先
3. **出力先** — コンサル文脈では engagement ディレクトリを「カレントプロジェクト」とみなし、
   `~/consulting/[slug]/drafts/design-team/` に出力させる
4. **デザイン後の再検査** — 本体セッションが deck md と完成 HTML の数値・出典を突合し、
   欠落・改変があれば /consult-check の K1/K3 を起動して精査する
5. **一般人評価の位置づけ** — B2C・一般読者向けにのみ案内（経営層向けは K5 の領分）。
   評価者はレンダリングを見られない（コードと文言からの体験推定）ことを CEO に添える
6. **パターン還流** — used_in の実績記録は design-team の Step 5 に委ね、
   デック用テーマとして常用したい意匠は themes/THEMES.md の追加手順で昇格する

## ファームナレッジ

エンゲージメントを跨いで知見を蓄積する仕組み（各案件が孤立しないための「ファームの記憶」）。台帳は `~/consulting/_firm/knowledge.md`。

**昇格規約:**
- 各エンゲージメントの納品時に「他の案件でも使える発見」を **0〜3件** knowledge.md に追記する
- 昇格できるのは **事実（出典確認済み）** と **検証済みの学び** のみ。仮説は昇格させない
- エントリ形式: `- [YYYY-MM-DD/元エンゲージメント] 内容（事実・出典: ... / 学び）`

**参照規約:**
- 分析・判断系スキル（/consult-analyze・/consult-decide・/consult-tokkyo・/consult）は開始時に
  knowledge.md を Read し、既知の事実を再調査しない（analyst への指示にも既知事実を含める）
- 300行を超えたらテーマ別ファイルへの分割を提案する

## 品質バー

全成果物に適用する最低基準:

1. **出典必須** — 事実主張には出典URL か資料名。出典を示せないものは「推定」「仮説」に降格
2. **検算必須** — 数値計算（合計・比率・成長率・加重スコア）は Bash（bc / python3）で再計算し、ログを analysis/ に残す
