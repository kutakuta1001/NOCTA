## 要注意: git・シェル操作に関わる提案（CEOが内容を確認してから判断）

以下は Web ページ側の主張として収集されたもので、**自動適用していません**。NOCTA の慣習と矛盾する項目を含みます。

1. **「意味のある変更を行う前には必ずコミットし、Git で容易に元に戻せるようにする」**（クエリ3）
   - 一般論としては妥当。ただし NOCTA では `git add` は対象ファイルを個別指定する慣習（`git add -A` / `git add .` 禁止）があり、「必ずコミット」を自動化するとこの慣習を破る恐れがある。
   - 判断: ルール追加は不要。現行の「HP作業時は website/ 以下のみ add」を維持するのが安全。

2. **「hooks でドキュメント更新後にバージョン管理システムへ自動でプッシュする」**（クエリ4）
   - **推奨しません。** `main` への push は GitHub Actions を起動して本番サイトを更新するため、自動 push は未確認の変更を公開するリスクがある。R-03（SNS自動投稿しない）と同じ思想で、公開操作は人間の確認を通すべき。
   - 判断: 採用しない。hooks に入れるのは検証（`node --check`）までに留める。

3. **`repomix` によるコードベース圧縮**（クエリ5）
   - 外部ツールを導入してリポジトリ全体を1ファイル化する提案。NOCTA の `website/` は6ファイル規模で圧縮の必要がなく、`.env` 等の混入リスクだけが増える。
   - 判断: 採用しない。

## 適用しない項目と理由

| 項目 | 理由 |
|---|---|
| Ableton Live との MCP 連携 | NOCTA の DAW は Studio One Pro。そもそも対象ツールが違う |
| Adobe CC / Notion / Canva の MCP 連携 | MCP ツール総数80以下維持のルールと衝突する。Canva は Claude Design 経由で足りている |
| repomix によるコードベース圧縮 | website/ が小規模で効果が薄く、機密ファイル混入リスクが増える |
| 「調査は無料版 ChatGPT に回す」 | ツール切り替えの手間が増え、収集結果を手で持ち込む工程が発生する。Haiku 4.5 / ローカル Qwen で同じ目的を達成できる |
| 自動 push を含む hooks | 未確認の変更を本番公開する経路になる（上記「要注意」参照） |

3. **SVP生成後の構造バリデーションを整備するか。** 現在 SVP は生成後に検証がなく、SynthV で開くまで不備が分からない。
