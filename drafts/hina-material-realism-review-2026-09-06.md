## A. 実装と説明の整合性

### A-1: `roughness` は配線されていない（Warning）

資料と `gems-data.js:14` は「roughness: 研磨面の粗さ（任意、0〜1）。省略時0.012」と記述するが、この経路は到達不能。

- `gems-data.js` の全24石に `roughness` フィールドが存在しない（`grep -c roughness` = 1、ヘッダのコメント1行のみ）
- `gems/index.html:999` が `gem3d.mount` に渡すのは `hardness` と `dispersion` のみで、`roughness` を渡していない

結果、`gem3d.js:617` の `gemData.roughness` は常に undefined で、**全透明石の研磨面が 0.012 固定**になる。従来は硬度由来で 0.010〜0.045 の幅があったため、石ごとの表面差は消えた。設計判断としては妥当（研磨面と硬度は独立）だが、「石ごとに指定できる」という説明は現状成立していない。

### A-2: 陳腐化した説明が2箇所（Warning）

**訂正（2026-09-07・Codex の指摘により）**: 当初この節で「`hardness` の説明行が消えた」と書いたのは
誤りだった。置き換えられたのは `gems-data.js:27`（3D節にあった重複説明「モース硬度（既存フィールドを流用）。
軟らかい石ほど表面roughnessを上げ自然な曇りを出す」）で、フィールド一覧の本文 `gems-data.js:14`
「hardness : モース硬度」は無変更のまま残っていた。`hardness` の説明は失われていない。

実際に陳腐化していたのは次の2箇所。

- `gems/index.html:999` のコメント「硬度依存roughness・石別dispersionに必要」→ hardness は roughness に影響しなくなった
- `gem3d.js:13` のヘッダが `gemData` に `hardness` を列挙したまま（実際には未使用）

### A-3: 「カボションは滑らかな法線を使う」は現行13石に効果がない（Warning）

`cut:"cabochon"` の石はオパール1件のみで `gem3d:"iridescent"`（別プリセット・元から `flatShading:false`）。
透明石にカボションは存在しないため、この式は全13石で常に true。将来用としては無害だが、
資料の「改善した」という書き方は実態と合わない。なお `cabochonGeometry()` 自体は今回変更されていない。

### A-4: 資料に記載のない挙動変更が2件（Warning）

## B. 公開前に修正すべき不具合

### B-1（Blocker）Hare: 既定ペン「筆」でタップしても何も描かれない

`iro/fude.js` の `begin()` は起筆として `segment(p, {x:p.x+0.01, y:p.y+0.01}, ...)` を呼ぶだけになった。
筆の分岐は毛先38本を `ctx.lineTo` + `lineCap='butt'` で描くため、**長さ 0.014px の線は実質何も塗らない**。
旧実装は `blot()` + 24px の `stamp()` を打っていた。

実測（1600×1200 の device px、alpha>4 の画素数と平均alpha）:

| 操作 | 変更前 | 変更後 |
|---|---|---|
| 筆・タップのみ | 30,352px / α46 | **15px / α16** |
| 筆・100px ドラッグ | 45,683px / α83 | 8,168px / α179 |
| カリグラフィ・タップのみ | 362px / α191 | 257px / α221 |
| 水彩・タップのみ | — | 4,768px / α28 |

実ページ（390px 幅）で「筆」のまま3回タップした結果が `iro-taponly-fude.png` — 紙は空白のまま。
筆は今回から**既定ペン**になったため、「開いて紙を叩く」という最初の操作が無反応になる。

修正案: `begin()` で起筆の点を明示的に置く（毛先を `lineCap='round'` にする、または半径 `w/2` の楕円を1つ置く）。

### B-2（Blocker）Ichi: tulip / bell に汎用の葉が二重に付く

`hana.js` の `drawFlower` は `o.leaves`（しずく形の葉1〜2枚）を **122行目のカップ分岐より前**に描く。
カップ分岐は自前の茎と葉を持つため、`f.leaves` を持つ tulip / bell は葉が二重になる。
さらに bell は分岐内で `ctx.rotate(Math.PI)` するため、**汎用の葉だけが回転せず**、吊り下がった鐘の下に
上向きの葉が2枚出る（`leaves-cup.png` の2番目）。

到達条件:
- 長押しの大輪は `f.leaves = [{ang:2.3},{ang:-2.3}]` を**必ず**持つ（`hana.js:894`）
- tulip は庭の `FORMS` 4種の1つ。通常の花は約半数が葉を持つ（`hana.js:845`）

つまり「大輪のチューリップ」は必ずこの状態になる。

修正案: カップ分岐に入る場合は汎用 `o.leaves` を描かない（分岐をカップ判定より前に移す）、または bell の回転を葉にも適用する。

## C. 判断が必要（見た目）

### C-1（High）Ichi: 満開スプライトの 160px 上限で大きな花がぼける

`hana.js:773` の `pixels = Math.max(8, Math.min(160, Math.ceil(span * dpr)))`。`span = f.r * 4` なので、
DPR2 では必要解像度に対して次の倍率で拡大表示される。

| 花の半径 r | span(CSS px) | 必要 device px | 実際のタイル | 拡大倍率 |
|---|---|---|---|---|
| 26（小） | 104 | 208 | 160 | 1.3× |
| 40（中） | 160 | 320 | 160 | 2.0× |
| 70（自生の大輪） | 280 | 560 | 160 | 3.5× |
| 104（長押しの大輪） | 416 | 832 | 160 | **5.2×** |

加えてタイル内は `tc.scale(160/416) = 0.385` で描かれるため、今回追加した細脈・縁のハイライト
（`lineWidth` 下限 0.30〜0.35px）が **0.12〜0.13 device px** に潰れて消える。
つまり今回の改善の主目的である細部が、いちばん大きく見える花でいちばん失われる。

さらに長押しの大輪は 3500ms かけてベクターで鮮明に開き、`bloom === 1` に達した瞬間に
5.2倍拡大のスプライトへ切り替わる。開き終わりでぼやける切り替わりが見える。

`sprite-compare.png`（左=ベクター / 右=スプライト、r=26/40/70/104）で差が確認できる。
実際の庭では `ab-new.png` の左の大輪が該当。

修正案: 上限を DPR 連動にする（`min(160 * dpr, ...)` または `min(320, ...)`）、
あるいは r が一定以上の花はキャッシュしない。メモリとのトレードオフは C-1 と B-3(memo) の兼ね合いで決める。

### C-2（High）Gyu: PT 環境の輝度が dark で 2.4倍・light で 1.2倍になった

**訂正（2026-09-07・Codex の指摘により）**: 当初の数値（dark 3.7倍・light 1.5倍）はテクスチャの
非加重平均で、球面の立体角を無視していた。正距円筒テクスチャは極を過大に数えるため、
上向きの3枚目のカード（dir (0, 1, 0.2)・sharp 12）の寄与が実際より大きく出ていた。
立体角（sin θ）で重み付けし直した値が正しい。

GradientEquirectTexture（512×512・Float32）を輝度（Rec.709）で実測:

| モード | 最大値 | 非加重平均 | **立体角加重平均** | 1.0超の立体角比率 |
|---|---|---|---|---|
| dark 変更前 | 2.711 | 0.0925 | 0.0899 | 0.45% |
| dark 変更後 | 5.586 | 0.3656 | **0.2133（2.37倍）** | 6.25% |
| light 変更前 | 3.169 | 0.5260 | 0.5206 | 0.74% |
| light 変更後 | 6.040 | 0.7992 | **0.6441（1.24倍）** | 10.05% |

方向性の結論は変わらない（dark は約2.4倍明るくなる）が、倍率は当初報告より小さい。

論点2つ。

1. 既存の `SPOT_PEAK = 2.6` には「HDR加算量の上限。上品なグリント程度に留める」という設計意図が
   コメントで明示されている。新カードの power 5.5 / 4.5 はこの上限を超える。
2. 資料は bgMode に触れていないが、カードは **light（白スタジオ）にも同じ量が加算される**。
   2026-07-12 の作業では白モードの白飛び回避（露出1.25・虹/bloom/後光を×0.4-0.6）を明示的に調整している。

### C-2b: 同心円ハローの原因は PT 追加光ではなく `reflectivity` 削除（切り分け実測で確定）

**訂正（2026-09-07・Codex の指摘により）**: 当初「同心円ハローはグラデーション環境が増幅されて
可視化されたもの」と書いたが、これは推論であって誤りだった。gem3d.js の変更を1項目ずつに分解して
ダイヤモンドの PT 静止画を6通り描画し、背景の輝度を実測して切り分けた（PT 環境は D/E/F/B で旧版に固定）。

| 組合せ | 石の外周リング平均L | 四隅平均L | 石の中心平均L |
|---|---|---|---|
| A 変更前（全項目そのまま） | 22.1 | **0.0** | 170.6 |
| D `reflectivity: 0.55` の削除のみ | 79.4 | **38.0** | 199.6 |
| E `clearcoat` 1.0→0.0 のみ | 22.0 | **0.0** | 170.1 |
| F 頂点ジッター縮小のみ | 22.9 | **0.0** | 175.2 |
| B 新 gem3d 全項目（PT 環境は旧） | 57.7 | 20.6 | 194.7 |
| C 新 gem3d + 新 PT 環境 | 61.2 | 20.3 | **215.9** |

読み取れること。

- **ハローは `reflectivity` の削除（IOR 復元）だけで発生する**。clearcoat と頂点ジッターは背景を
  1ポイントも動かさない（四隅 0.0 のまま）。
- **PT の追加光は背景にほぼ影響しない**（C vs B の四隅 20.6→20.3）。追加光の効果は石そのもので、
  中心輝度を 194.7→215.9（+11%）に上げ、ファセットにスタジオ反射を作る。
- clearcoat の除去は**ハローを弱める方向**に働いている（D の四隅 38.0 → B の 20.6）。表面反射が減った分、
  裾も弱まる。
- 同心円のバンド構造は bloom のミップ連鎖に見えるが、機構の断定は避ける。確定しているのは
  「どの変更行が原因か」であって「どのポストプロセスが描いているか」は未検証。

つまり判断は2つに分かれる。

- **ハローを消したい場合の手当ては PT 追加光ではなく bloom / 露出側**。IOR 修正は正しい変更なので
  巻き戻す対象ではない。
- **PT 追加光の是非は「石が11%明るくスタジオ反射が付くのを好むか」だけの判断**になる。

- `dia-sheet.png` — 変更前/変更後のダイヤモンド。ファセットの明暗と内部反射が明確に良くなっている。
- `halo-sheet2.png` — 上記6通りの比較。
- `pt-sheet.png` — オパール（カボション）の dark / light 比較。white studio は破綻していないが全体に明るい。

## D. 既存機能への影響（Warning）

### D-1: `pointerleave` を外し `setPointerCapture` 一本化

`fude.js` は `pointerleave` ハンドラを削除し、`setPointerCapture` に依存する形になった。
`setPointerCapture` は try/catch で黙って失敗を許容するため、capture が取れない環境では
ストロークが解除されず、`begin()` の `if (disposed || stroke || ...) return;` により**以後まったく描けなくなる**
（clear / resize / pen 切替までロック）。iPhone Safari 実機が未検証であることと重なるリスク。

修正案: capture 取得の成否を保持し、失敗時のみ `pointerleave` / `window` の `pointerup` を張る。

### D-2: coalesced event ごとに `getBoundingClientRect()`

`point(e)` が毎回 `getBoundingClientRect()` を呼ぶ。`move()` は `getCoalescedEvents()` の全件に対して
`sample()` を回すため、高レートのペン入力では1フレームに20回以上のレイアウト読みが発生する。
1フレーム1回のキャッシュに寄せられる。

### D-3: スプライトのメモリ（iOS 未検証）

`MAX_FLOWERS = 400`。うち緑（sprig/fern/umbel/floret、なぞりの約35%）を除いた約260件が
160×160×4B ≈ 102KB のタイルを保持し、最大で **約27MB（全件が花なら41MB）**。
破棄は `detach()` 時とキー変化時のみで、画面外・加齢後も保持され続ける。
iOS Safari は canvas の総メモリと枚数の制約が厳しく、数百枚のオフスクリーン canvas は
白抜け・描画欠落の実績がある領域。実機確認が必要。

### D-4: tulip 用の分岐がデッドコード

`form === 'tulip'` は 122行目で早期 return するため、その後の
`layers = ... 'tulip' ? 2`、`count = form === 'tulip' ? 3 : n`、`wid ... 'tulip' ? 0.66` はすべて到達不能。
読み手を誤らせるので削除するのが望ましい。

### D-5: 起筆の毛先角度が固定 45度

`begin()` の `segment(p, {x:p.x+0.01, y:p.y+0.01})` により、初回の毛先法線は常に 45度方向になる。
B-1 の修正時に一緒に整理できる。

## F. 確認できた改善

1. **IOR 上書きバグは実在した**。three r180 で `MeshPhysicalMaterial({ior: 2.42, reflectivity: 0.55})` を
   実際に構築して確認: `reflectivity` の setter が `ior = (1+0.4v)/(1-0.4v)` を代入するため、
   **データの IOR に関係なく全透明石が実効 1.5641 に固定**されていた（ダイヤ 2.42 → 1.5641、
   コランダム 1.77 → 1.5641、ベリル 1.58 → 1.5641）。オブジェクトリテラルで `ior` の後に
   `reflectivity` を書いていたため上書きされていた。診断・修正ともに正しい。
2. ダイヤモンドの静止 PT が明確に良くなった（`dia-sheet.png`）。ファセットの明暗・ガードルと
   パビリオンの読みやすさ・輪郭の対称性がいずれも向上。
3. **sakura の切れ込みの修正は実害の解消**。旧実装は地色の三角形を花弁の上に塗っていたため、
   隣の花弁に重なった箇所に地色のパッチが乗っていた（`forms-old.png` の sakura に見える暗い三角）。
   新実装は実輪郭でくり抜いている。
4. 7形状は全体として大幅に良い（`forms-new.png`）。tulip / bell のカップ、layered の八重、
   kiku の層構造はいずれも成功している。庭全体の比較（`ab-old.png` / `ab-new.png`）でも、

### C-1 + D-3: 適応上限＋総量予算＋LRU 解放

Codex 推奨どおり「解像度を上げる」を「総キャッシュ画素数の上限」と「解放方針」とセットで実装した。

- `SPRITE_MAX_SIDE = 320`（1枚の一辺の上限）
- `SPRITE_BUDGET_PX = 8 * 1024 * 1024`（総画素数＝RGBA で約32MB のハードな天井）
- `SPRITE_SIDES = [64, 96, 128, 160, 192, 224, 256, 320]`（一辺の階段）

予算の主機構は**枚数が増えるほど新規スプライトを小さく作ること**。枚数 n での一辺は
`sqrt(SPRITE_BUDGET_PX / n)` に収まるので、総量は予算へ自然に漸近する。
既存スプライトは解像度を理由に作り直さない（階段をまたぐ度に全輪が再生成される事故を防ぐ）。
裏を取る保険として、予算超過時は「今フレームに使っていないスプライト」を古い順に解放し（LRU）、
それでも空かなければ確保を諦めてその輪だけベクター描画に落とす＝メモリは予算内に固定される。

解放は7経路すべてに接続した: FIFO 排出（`flowers.shift()` 3箇所）・開花途中/退場中（bloom<1）・
`clear()` の reduce 経路と突風経路・退場完了・`detach()`。
